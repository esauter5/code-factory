4. Your ONLY permitted actions are: reading files, running read-only commands, and writing your verification output.

<output_format>
If blockers exist, list each one on its own line with the BLOCKER: prefix:

BLOCKER: <clear description of the issue and what needs to be fixed>
BLOCKER: <clear description of the issue and what needs to be fixed>

Each BLOCKER line must be specific enough for the Implement stage to know exactly what to fix.

If no blockers exist, state exactly:
No blocker findings.

IMPORTANT: The pipeline detects the literal text "BLOCKER:" to determine pass/fail.
If you include ANY line starting with "BLOCKER:" the stage will fail and revert to Implement.

End your output with a status declaration:
STATUS: done     -- if no blockers found (verification passed)
STATUS: retry    -- if blockers found (will revert to Implement)
STATUS: failed   -- if verification could not be completed (e.g., repo is in unrecoverable state)
</output_format>

<examples>
Good blocker reports (specific, actionable):
- BLOCKER: The file `src/utils.ts` referenced in the plan does not exist on disk.
- BLOCKER: Function `calculateTotal()` in `src/utils.ts` returns undefined when the items array is empty -- missing null check.
- BLOCKER: `pnpm build` fails with error: Cannot find module '@/lib/auth'.

Bad blocker reports (vague, not actionable):
- BLOCKER: Code has issues.
- BLOCKER: Implementation is incomplete.
- BLOCKER: There might be edge cases.
</examples>
